# 产品方向

更新日期：2026-10-30。状态：布局和功能照 Rebased，M7 外观改为 Liquid Glass、代码清晰度优先，并同步设计 macOS / Windows 外壳；M6 已合入 main，M7 访谈已确认，进入实施准备，已确认 Q176–Q199；既有遗留项仍在 backlog。

## 定位

Revia 是一个照 Rebased（基于 IntelliJ 平台的开源 Git 客户端）的布局和功能、采用 Liquid Glass 外观的轻量桌面 Git 客户端：不依赖 JVM，在 Rebased 的功能之上多出审阅标记、回收区和写前校验（Q118、Q189）。最终提供 macOS Apple Silicon 版、Windows x64 安装版和 Windows x64 便携版；首版只做 macOS，Windows 放在首版验证之后（Q55）。布局、功能和交互照本机安装的 Rebased 1.1.22；保留 VS Code 颜色主题、系统界面字体和可配置代码字体，玻璃效果不得牺牲代码与 diff 可读性（Q117、Q132、Q133、Q190）。

明确不做：

- **fork Rebased**：照它的功能和界面自研，不基于 IntelliJ 平台（[ADR-0011](./adr/0011-rebuild-like-rebased-not-fork.md)）。
- **GitButler 式的虚拟分支**：不在 Git 之上发明自己的工作流模型。
- **IDE 里的 Git 插件**：Revia 是独立应用，与编辑器并行使用。

## 取舍顺序

三个特点冲突时，按以下顺序取舍（Q5）：

1. **提交可信**：清楚区分未暂存改动、已暂存改动和最终提交内容；不偷偷改工作区；不自动执行危险操作。
2. **审阅舒服**：diff 清楚，键盘操作顺手，文件切换快。
3. **项目切换高效**：多个仓库和 worktree 的状态一眼可见。

例如“更快”和“更稳”冲突时选更稳：每次写操作前都重新读取仓库状态，即使多花几十毫秒。

## 核心工作流

审阅 diff → 选择变更 → 提交（Q2）。首版的其他能力都围绕这个闭环取舍。

### M2 写操作范围

M2 每次只操作一个文件或一个 hunk，不增加文件多选、“全部暂存”和批量丢弃（Q79）；M4 起按 Q120 支持多选、全部暂存和多个文件一起丢弃。整文件与 hunk 操作的适用范围如下（Q81–Q83）：

| 文件情况 | M2 允许的 Git 写操作 | 限制 |
| --- | --- | --- |
| 普通已跟踪文本文件 | 整文件或按 hunk 暂存、取消暂存、丢弃未暂存改动 | 不一步丢弃已暂存内容 |
| 二进制文件、仅权限变化、重命名 | 整文件暂存、取消暂存、丢弃未暂存改动 | 不提供 hunk 操作 |
| 未跟踪文件 | 整文件暂存 | 不提供按 hunk 暂存、丢弃或删除 |
| 符号链接、子模块、无法无损处理的非 UTF-8 路径 | 无，只读并说明限制原因 | 中文、空格等正常文件名不在限制之列 |
| Git 仍标记为未解决冲突的文件 | diff 中只读；M4 起在合并页签中解决，点“应用”后标记为已解决（Q143） | 不通过普通暂存隐含地标记冲突已解决 |

只读限制优先于其他文件类型的操作能力。完整的进行中操作识别仍在 M3（Q82）；冲突在 M4 起用内置三方合并解决，取代 Q82 原定的外部合并工具入口（Q143）。

整文件快捷键不随 diff 焦点改变作用范围；hunk 使用明确的操作按钮，不根据鼠标或屏幕位置猜目标，具体入口见 [UI 方向](./ui-direction.md#快捷键作用范围)（Q93）。

## 审阅标记

审阅标记以文件为单位，记录的是“HEAD 中的版本 + 工作区中的版本”这一对内容（Q20）：

| 场景 | 结果 |
| --- | --- |
| 暂存或取消暂存这个文件 | 标记保留，内容没有变化 |
| 在编辑器中修改了这个文件 | 标记失效 |
| 只提交了这个文件的一部分 | HEAD 变化，剩余部分的标记失效，需要重新审阅 |
| 重启 Revia | 标记保留；内容变化过的标记自然失效 |

- 标记保存在 Revia 自己的数据目录中，按 worktree 分开。
- worktree 移动、删除重建后身份不明确时，不因路径相同而继承原审阅标记（Q87）。
- 标记不阻止提交，只在提交按钮旁显示审阅进度，例如“已审阅 3/5”。
- 宁可失效得勤一点，也不能该失效时没失效。
- 文件列表中已审阅文件显示小图标，diff 页签工具栏的“标记为已审阅”按钮只切换标记、不跳转（Q121）；⌥⌘R 只标记、不取消，再按文件列表顺序寻找下一个未审阅文件，同文件跨组去重、末尾可回到开头，并展开目标所在折叠组。全部已审阅时留在当前文件并提示（Q94）。

## 提交

### hooks

- hooks 照常执行，目标是和在终端里进入这个 worktree 再执行 `git commit` 的效果一致（Q21）。
- 运行环境按 worktree 解析，详见 [技术方向](./technical-direction.md#运行环境)。
- hook 的输出实时显示；失败时保留已经写好的提交信息。
- 每次提交可以勾选“跳过 hooks”，默认不勾，提交后自动复原。这是环境出问题时的退路。

### 提交前快照

- 存在部分暂存的文件时，提交前自动把这些文件的工作区内容存入回收区（Q22）。
- 提交完成后，如果 hooks（例如 lint-staged 格式化）修改了工作区或暂存区的文件，在提交结果中列出这些文件。

### 修改上一次提交

- 提交区提供“修改上一次提交”开关，对应 JetBrains 的 Amend；勾选时预填上一次的提交信息（Q23）。
- 上一次提交已经包含在上游跟踪分支中（按本地记录判断）时，显示警告并要求再次确认。
- 有进行中的操作时不可用。

### 提交信息框

- 单个多行输入框；首行超过 72 个字符时提示，不阻止提交（Q24）。
- 读取 Git 的 `commit.template` 配置。
- 可以从最近 20 条提交信息中选用。
- 每个 worktree 单独保留未完成的草稿，切换时不丢失。
- 提交信息为空时不能提交。

### 签名

遵循 Git 配置，不提供签名相关设置，也不专门测试签名场景；签名失败时原样显示 Git 的错误（Q25）。

## 外部修改

- M2 只实时监视当前选中的 worktree 及相关 Git 元数据，自动刷新状态；切换 worktree、回到前台时重新核对，并保留手动刷新（Q26、Q88）。不为全部登记仓库常驻监视，完整概览随 M4 侧栏完善。
- 写操作执行前校验用户看到的 diff 是否仍然有效，对不上就拒绝执行、刷新界面并提示“文件已变化，请重新确认”，见 [ADR-0005](./adr/0005-write-ops-carry-diff-fingerprint.md)。
- M2 的校验范围是操作涉及的文件及相关版本、状态和路径；无关文件变化不阻止操作。即使只操作一个 hunk，同一文件其他部分的相关变化也必须拒绝，见 [ADR-0009](./adr/0009-file-scoped-write-fingerprints.md)（Q80）。
- 遇到 `index.lock` 时短暂重试，仍被占用就提示用户，绝不删除锁文件。
- 刷新后优先保留原组中的同一文件，其次跟随移到另一组的同一文件；文件完全离开改动列表时选原位置附近的文件，无可选项则清空 diff。更新后的旧 hunk 和旧确认失效，不能把旧序号套到新快照（Q89）。
- 文件监视失败时持续提示“自动刷新不可用”，保留手动刷新与回到前台核对；只要写前仍能重新读取状态且指纹校验通过就允许操作，读取或校验失败则拒绝写入，不静默降级（Q95）。

### 写操作执行中

- 允许继续浏览和切换文件、worktree，但切换界面不改变已发起操作的目标（Q90）。
- 同一个 worktree 一次只执行一个 Revia 写操作，期间禁用该 worktree 的其他写入口，不把连续点击积压成操作队列。
- 结果提示归属原 worktree，旧响应不得覆盖当前界面。
- 回收区保存后操作中断（例如执行途中应用退出）、Git 超时等导致结果无法确定时，保留已保存记录，显示“结果待核对”，重新核对真实状态；不自动继续丢弃、恢复或重跑命令。下一次写入基于重新读取的状态，超时不等于没有发生变化（Q91）。
- 写操作期间请求关闭窗口或退出时，先保留窗口和进程，提供“等待完成后关闭／退出”或“留在应用”；不为关闭窗口杀掉 Git，不提供未经验证的取消写操作。正常完成并记录结果后执行原请求；若结果待核对，先展示情况，不静默退出。系统强退或崩溃仍按 Q91 处理（Q96）。

## 回收区

- 保存操作前的文件状态（包括丢弃前内容、提交前快照和覆盖前保护），M6 增加被删除 stash 的完整归档（Q9、Q22、Q156、Q160）。
- 普通文件回收记录包括时间、来源和对应文件的工作区状态，绑定原仓库与原 worktree，存放在 Revia 的数据目录中，不放进仓库（Q29、Q87）。
- M2 即使只丢弃一个 hunk，也保存该文件丢弃前的完整状态：内容、相关路径、存在状态和可执行权限。恢复回到这次丢弃前的工作区状态，不改变暂存区，不自动重放反向补丁；接受由此增加的存储占用（Q85，见 [ADR-0010](./adr/0010-recovery-records-preserve-worktree-state.md)）。
- 恢复时，当前状态与丢弃完成后的状态一致才直接写回；不能拿当前状态与保存的丢弃前内容比较来判断是否有后续变化。发生后续变化时不覆盖，文本用只读 diff 对比当前内容和保存内容，由用户自行复制需要的部分（Q29、Q85）。
- 二进制恢复遇到后续变化时，展示两个版本的大小、记录时间等信息；保存版本可另存为未被占用的新路径，不提供强制覆盖原文件（Q86）。
- worktree 移动、删除重建后身份不明确时，不按路径相同猜测迁移，不直接恢复到新目录；记录仍保留供查看直到正常到期（Q87）。
- 超过 14 天自动清理。
- 普通文件回收不借用用户的 `git stash` 或 reflog：stash 会出现在用户自己的 `git stash list` 中，reflog 也不保护从未提交过的内容。
- M6 删除 / 清空 stash 前，把条目的完整内容独立存入 Revia 回收区，保留 14 天，不依赖用户仓库继续保留对象，也不增加隐藏引用。取回时只恢复为原仓库 stash 列表中的条目，不直接改工作区或暂存区，见 [ADR-0012](./adr/0012-stash-recovery-outside-user-repository.md)（Q160）。

## 合并工具

- 冲突用内置三方合并解决，照 Rebased 的合并窗口：冲突组、冲突对话框、三栏合并页签、“应用”后标记为已解决。合并结果由 `git merge-file` 生成，Revia 不自己算合并；覆盖工作区文件前先存回收区。M4 实现，设计见 [M4 内置三方合并](./milestones/m4/merge-design.md)（Q143）。
- 继续、中止、跳过在 M6。
- 外部合并工具保留为可选设置，M6 实现：Revia 不修改用户的 Git 配置（Q12、Q28）；用户配置了 `merge.tool` 时直接使用；没有配置时，第一次需要时列出 Git 检测到的可用工具让用户选一次，保存在 Revia 的设置中。

## M6：冲突与历史

以下为 Q156–Q172 已确认内容，实施范围见 [M6 规格](./milestones/m6/spec.md)。Codex 规划、审查和验收，同一个 Paseo / Pi 会话在独立 `m6` worktree 一次整包实施，完成后统一审查验收（Q155、Q172）。日志日期列折行按 [backlog 07](./milestones/backlog/07-log-date-column-wrap.md) 一并修复，界面语言与 x18n 提前到 M6（Q163）；Q154 的其他已知问题不自动纳入。

Rebased 安装资源与 x18n 官方工作流的事实、来源和未确认边界见 [M6 资料核对记录](./milestones/m6/references.md)；不能用静态核对代替运行时验收。

### stash

- 保存对话框照 Rebased，只提供说明和“保留暂存区”，不增加“包含未跟踪文件”（Q156）。不把没有这个选项等同于已经确认底层是否包含未跟踪文件；实际行为由本机 Rebased 对照核实。
- 应用提供“应用后删除”（默认不勾）、“恢复暂存区”和“作为新分支”；应用前先存回收区。
- 删除、清空都先确认并存回收区，不能只移除 Git 中的条目而没有可取回内容。
- 删除条目的完整内容保存在 Revia 自己的回收区目录，Git bundle 只是可选形式，不在用户仓库增加隐藏引用。取回为 stash 条目，不直接写工作区或暂存区（Q160）；普通文件恢复继续遵守 ADR-0010。
- 其他开关默认值按本机 Rebased 核对，不能将静态资源观察冒称为真实桌面验收。

### 未提交改动与历史操作

- 不一律要求工作区和暂存区干净（Q157）。rebase 自动保存未提交改动，之后恢复；自动保存一律用 stash，不做 Shelf，也不增加“清理工作区方式”设置（Q161）。
- cherry-pick、revert 会覆盖未提交改动时，照智能检出提供“先 stash 再执行再恢复 / 强制覆盖 / 取消”。保存或覆盖前先存回收区。
- 操作因冲突暂停时保留自动保存的 stash，等用户完成或中止原操作后再恢复。恢复本地改动仍有冲突时保留 stash 并提示，不自动删除、不重复尝试；手动应用即使勾选“应用后删除”，冲突时也不删除（Q162）。
- 自动保存后发通知，说明本地改动已在相应操作前存为 stash，并提供“查看 stash”入口。自动保存的条目说明明确由 Revia 在哪个操作前保存。
- 交互式 rebase 支持调整顺序、改提交信息、squash、fixup、删除提交和暂停编辑，不提供任意 shell 命令；范围含 merge 提交时按钮不可用并说明原因，不静默展平（Q158）。
- 在明确的“编辑”停点允许 amend 和新建提交，以便拆分提交，之后单独点击“继续”；冲突停点仍不允许普通提交，不放开所有进行中操作的提交门禁（Q166）。
- 空 cherry-pick 的设置为“跳过 / 创建空提交”，默认跳过；执行确认页显示本次采用的策略，用户确认后按策略处理。结果列出因空提交跳过的提交，这是 Q123 的窄例外，不用于冲突时自动继续或重启后续跑（Q165）。

### 文件历史与 blame

- 文件历史默认当前分支，可切到所有分支（Q159）。
- blame 提供“忽略空白”“检测文件内移动”“检测跨文件移动”和“查看上一版本的 blame”；其他默认值与细节在后续追问中补齐。

### 界面语言与文案维护

- 简体中文 / English 的界面语言切换从 M7 提前到 M6，范围包括既有界面和本轮新增功能，不只翻译 M6 新增按钮。首次启动未设置语言时，中文系统使用简体中文，其他系统使用英文；用户选择后即时生效并持久化，保留页签、提交草稿和合并编辑内容（Q163、Q164）。
- 翻译和文案维护改用 [x18n Agent workflows](https://x18n.dev/agents/workflows)。官方工作流用 CLI 的 `--json` 查询与写入语言资源，再用 `x18n check` 校验；不把安装文案工具本身视为已经完成运行时语言切换。
- Rust 用户可见报错也须双语：返回稳定错误类型和参数，由前端生成当前语言的文案，不把整段原中文错误藏进参数，见 [ADR-0013](./adr/0013-localize-structured-user-errors-at-presentation.md)。用户估计现有 Rust 层约 784 处中文字符串，实际实施须分类用户文案和内部日志，不能把数量当作完成依据。
- 不把仓库内容、用户提交信息或 Git 原始输出混入待翻译的产品文案；调试与测量日志不翻译。
- Pi 实施时使用用户已安装的 x18n MCP、`x18n` / `x18n-check` skills；派发前核对 Pi 实际可见的工具与技能，不能把 Codex 的安装状态当作 Pi 已加载。语言资源通过 x18n 查询、写入、校验，不直接手改；源语言 `zh-CN`、目标 `en`、语义分组和 camelCase 末级键保留，术语见 [文案规则](./milestones/m6/i18n-proposal.md)，提交前快照使用 `Snapshot Before Commit`（Q169、Q170）。
- 现有函数式文案改为占位符，动态查表改为完整字面量键映射。check 验证翻译和占位符；独立的 extract --list 扫描发现可见写死中文时失败，调试与测量日志用 x18n-ignore 标注（Q169、Q171）。
- 英文窄窗口须检查布局；x18n 须检查界面代码无写死中文。真实 Git 测试触发 Rust 生产错误，核对结构化载荷后经生产英文格式化链路断言最终可见英文，不能仅断言错误码或以模拟报错替代（Q168）。

## 验证计划

分两个阶段（Q14）：

1. **自用**：连续 2 周，自己 Vue 和 Swift 项目的日常提交都通过 Revia 完成。每次不得不回到终端或 IDE，都记录原因。这个阶段不做应用签名。
2. **试用**：邀请 3–5 位熟悉 JetBrains Git 的开发者试用 1 周。试用结束后他们仍主动用它审阅和提交，才算成功。试用用的是未签名的版本（Q63），随包附一页带截图的“首次打开说明”：在“系统设置 → 隐私与安全性”中点“仍要打开”。

**硬性红线**：只要出现一次“提交内容与界面显示不一致”或“改动丢失”，就暂停新功能，先修复。

### M2 长期运行验收

Q78 补充 Q53 的验收口径，不把历史报告中的卡住记录当成当前版本已经复现的故障：

- M2 第一项仍是用当前正式工程复现和验证长期运行问题，不以每轮重启应用的短测替代。
- 使用 release 构建、可见窗口，在固定的一组文件和 worktree 上同进程连续操作 30 分钟，包括切换文件、切换视图和滚动。
- 允许首次加载和填充缓存时的内存增长；热身后不能持续增长，同时观察 Rust 主进程与相关 WebView 进程。WebView 进程是否持续增长，按“内存压力后仍保留的内存”判定（Q98）：约每 5 分钟发送一次 WebKit 低内存通知，约 10 秒后取样；未经内存压力的普通取样包含尚未回收的垃圾和缓存，照常记录，但不单独作为不通过依据。
- 若无法复现旧问题，但长测达标并保留操作过程和内存趋势证据，可以继续 M2；报告写“未复现，长测通过”，不能写“已修复”。
- 若发生卡死或内存持续增长，先修复再继续；M2 功能完成后重新进行长测。
- [并排视图偶发慢帧](./milestones/backlog/01-split-scroll-hitch.md) 继续留在 backlog，不作为 M2 必须解决的项目；不得破坏已有滚动表现。若排查证明与长期卡住同源，再依据证据讨论处理范围（Q84）。

### M2 正确性与异常验收

采用两层验证，不以其中一层替代另一层（Q92）：

## 安全边界

以下约束来自已确认的选择，后续设计不得突破：

- 写操作前重新校验状态，不基于过期界面执行（Q5、Q26）。
- 丢弃前、以及存在部分暂存文件的提交前，先把内容存入回收区；回收区独立于 Git（Q9、Q22）。
- 继续、中止、跳过进行中的操作只在用户明确点击后执行，绝不自动执行；中止、跳过先确认，并把受影响文件的当前内容存入回收区（Q123）。
- 改写历史的操作执行前确认；会覆盖工作区内容的操作先存入回收区；强制推送只用 `--force-with-lease`；改写已在上游的提交时额外警告（Q123）。
- 不删除 Git 的锁文件，不修改用户的 Git 配置（Q26、Q28）。
- 界面显示的 hunk 与实际暂存的补丁来自同一份 Git 输出（Q18，见 [ADR-0004](./adr/0004-hunks-come-from-git.md)）。
