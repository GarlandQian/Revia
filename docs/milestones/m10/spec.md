# M10：三项架构深化

Status: done
日期：2026-11-09
基线：2b1e504479de5de9b2fc399dd81172df42d9d52c

## Problem Statement

打开、手动刷新、后台环境就绪和写后核对分散维护激活与监视归属；完整环境的解析、安装与就绪发布分散维护先后关系；生成提交信息的请求状态与目标草稿各自维护归属。调用方须理解这些时序才能正确使用 module，现有部分测试仅覆盖独立判定或自行拼装的流程，难以验证真实接线。

用户在架构报告后选择“全部”，并对推荐方案回复“按推荐”。本轮深化三个既有 module，目标是增加 depth，让行为与验证具备 locality，并让多个入口获得 leverage；保留已确认的产品行为。

## Solution

1. Worktree 激活与刷新：由同一 module 负责激活、监视归属、读取接收、错误资格与原目标核对；显示层表达打开、刷新等意图。
2. Worktree 运行环境：由同一 module 持有从临时可读到完整环境就绪的生命周期，把会话安装、替换与通知顺序收在 implementation 内。
3. 生成提交信息：由同一 module 持有请求及目标输入的归属，集中处理流式接收、取消、失败、撤销与切换失效。

## User Stories

1. 作为用户，我希望打开 worktree 后先看到文件列表，其余内容随后补上。
2. 作为用户，我希望手动刷新后继续收到文件监视引起的变化。
3. 作为用户，我希望完整环境就绪后的重读也保持自动刷新可用。
4. 作为用户，我希望快速 A→B→A 切换时，旧快照和旧错误不会覆盖新界面。
5. 作为用户，我希望写操作结束后核对原 worktree，即使已经切走。
6. 作为用户，我希望监视失效时仍有提示、手动刷新和回前台刷新。
7. 作为用户，我希望审阅标记、所选文件和 diff 指纹保留既有版本语义。
8. 作为用户，我希望按各自 worktree 加载完整环境，hooks、提交、网络和终端等待其就绪。
9. 作为用户，我希望手动指定的 Git 优先，失效的 Git 记忆能沿既有规则回退。
10. 作为用户，我希望重新加载环境后，旧解析结果不能让新一轮提前就绪。
11. 作为用户，我希望环境切换不绕过写锁，也不在被替换的旧会话上执行写入。
12. 作为用户，我希望生成提交信息只改动发起时的目标输入。
13. 作为用户，我希望取消或失败恢复生成前文字，完成后可以一步撤销。
14. 作为用户，我希望切换 worktree 或开始新输入后，迟到的生成事件不再覆盖它。
15. 作为用户，我希望首次发送和替换确认仍生效，生成的内容沿用草稿保存及提交检查。
16. 作为维护者，我希望测试通过实际生产 interface 覆盖这些完整时序。

## Implementation Decisions

- Worktree 激活与刷新 module 收拢共同生命周期，保留有 depth 的 SnapshotGate、ReviewOverlay、读取合并和恢复规则作为 implementation。不能只把原闭包搬文件、留下调用方继续手动同步 activation 与监视。
- 打开、手动刷新、环境就绪、重载和写后核对进入共同生产 interface；原目标真实核对与当前界面发布资格保持区分。文件列表渐进加载不被监视登记或次要取数阻塞。监视事件合并、写期间暂停、滚动让行保留。
- Worktree 运行环境 module 集中会话创建、临时 Git 选择、完整环境解析、安装、替换、就绪与重载失效。安装成功（或既定回退）先于 ready；失效代次不能发布缓存、ready 或事件。公开调用方不再组合 begin/install/complete 协议。
- 保留现有 ShellResolver seam；生产登录 shell adapter 和受控解析 adapter 均实际使用。Git 仍通过 Rust 调用系统 CLI；不建立通用进程抽象。
- 等待中的写入若对应会话被替换，按既有结构化错误拒绝，不能自动重放。下一次显式操作取得新会话；原会话实际写入完成前环境替换等待写锁。
- 生成提交信息 module 与现有提交输入状态共享目标资格，持有 requestId、worktree、输入代次、生成前内容及撤销资格；显示层不再自行维护另一套请求归属。通过现有 IPC 事件 adapter 接收事件，受控事件 adapter 驱动测试。
- 切换或目标输入失效时立即取消请求资格，再请求后端取消；迟到 delta、done、error、invoke 拒绝以及异步确认回包均不能覆盖新目标。取消、失败与撤销只恢复仍归属于本次生成的输入，不覆盖后来手动编辑。
- 保留 AI 的发送内容、首次确认、替换确认、语言、凭据和日志排除规则；传输与凭据仍在 Rust。生成不自动提交。
- 不以 module 行数衡量 depth。deletion test：保留删除后会把规则散回调用方的既有 module，移除被共同生产 interface 替代的重复协调。
- 不变更持久数据格式、不新增产品设置、不新增依赖或测试框架；具体方法名及内部结构由实施方选择。

## Testing Decisions

- interface 是测试入口。前端沿用 Node 行为测试，执行 App 实际使用的生产 module，使用受控 Promise / 事件；不得以源码字符串断言代替时序证明。
- 刷新覆盖：打开→手动刷新→监视事件；环境就绪→监视事件；A→B→A 的旧快照与错误；切走后的写后原目标核对；写期间合并刷新；监视降级。既有审阅与关闭契约测试保留。
- 环境沿用真实 Git 临时仓库、独立应用数据及 ShellResolver；覆盖环境安装先于等待操作继续、Git 改变替换会话、旧会话等待写入被拒绝、重载迟到结果不发布、双 worktree 隔离、手动 Git 与失效记忆回退。使用现有受控阶段与 Barrier，不靠延长 sleep 把竞争隐藏。
- AI 覆盖流式完成、取消、失败、一步撤销、A→B→A、新请求接替旧请求、取消在请求登记前发生、迟到事件/请求失败、手动输入后旧事件与撤销失效。经生产 module 与提交输入组合验证，不仅测试事件 reducer。
- 同一批修改完成后集中验证：前端类型、lint、build，现有 Node 行为测试，以及完整 Rust 测试（共享会话契约）。Rust 默认并发的结果如实保留；必要的串行诊断不替代原始结果。
- 真实 Git 测试只使用 tempfile 独占的新仓库；测试不访问真实 AI 服务、凭据库或用户仓库。若触及 locale，遵守 x18n；本轮预期复用已有文案。
- 规划方审查后用固定源码构建，在 macOS 可见窗口核对打开、切换、刷新及本机模拟 AI 的交互。Windows 真实桌面和真实 AI 服务仅由相应环境验证，不以本机检查替代。不重新扩大历史未达标项。

## Out of Scope

新功能、外观修改、持久数据迁移、AI 聊天或审阅、真实 AI 调用、发布新版本、远端推送、PR，以及 M8/M9 尚未完成的 Windows 实测与历史性能问题。
