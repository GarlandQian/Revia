# M1 实施计划

更新日期：2026-10-20。状态：待评审（评审意见写入 [m1-review.md](./review.md)，标明“用户已同意”后开始）。

本文只记录 M1 的实施方案，不产生新的设计决策。所有取舍都在文末“待评审确认”列出。

## 一、目标与范围

按 [AGENTS.md](../../../AGENTS.md) 的“当前阶段：M1 只读”，M1 分两步：

| 顺序 | 任务 | 来源 |
| --- | --- | --- |
| 1（先做） | 改造 diff 传输：按可见范围分批取数据，消除快速滚动时的空白 | [技术方向](../../technical-direction.md#diff-传输与渲染m1)（Q46） |
| 2（再做） | 初始化正式工程，实现添加仓库、读取状态、文件列表、显示 diff | [产品方向](../../product-direction.md#实施顺序) |

**M1 只读**：不实现暂存、取消暂存、丢弃、提交，也不产生任何写操作。

### 关于执行顺序的说明

实施顺序是“先传输改造、后正式工程”，而“不修改原型目录”意味着改造必须落在正式工程里。计划的做法是：

1. 先在仓库根目录初始化正式工程，并只实现**能跑通测量所需的最小骨架**（窗口 + 可切换的测量入口）；
2. 在骨架上完成传输改造并按验收标准测量；
3. 通过后再补齐只读界面（添加仓库、文件列表等）。

## 二、任务一：diff 传输与渲染改造

### 2.1 M0 现状与要解决的问题

M0 实测（8309 行 hunk、16 515 行参与高亮）：

- `get_diff` 一次返回全部文件与 hunk，JSON 载荷 1.15 MB；首屏 207–228 ms 中 **IPC 占 164–187 ms（73–82%）**；
- 前端持有全部行并整表构建渲染模型，可见区域外没有数据缺口，但 **24 行 overscan 跟不上快速滚动**，会出现空白；
- 高亮已经按行分块、异步到达，不影响首屏（这部分设计继续沿用）。

M1 要把“传输”和“渲染”的粒度都对齐到**可见范围**：Rust 侧保留完整模型，前端只取当前可见（加预取）的那一段。

### 2.2 传输协议

Rust 层新增/改造的命令（前端只能调用这些固定、带类型的操作）：

| 命令 | 入参 | 返回 | 估计载荷 |
| --- | --- | --- | --- |
| `open_workspace` | worktree 路径 | git 路径与版本、登录 shell 解析结果、状态指纹 | < 2 KB |
| `list_changes` | worktree | 三组文件（未暂存 / 未跟踪 / 已暂存）的元数据：路径、状态、是否二进制、增删行数、hunk 数与位置、两种视图的行数、语言 | 单文件 < 1 KB；500 个改动文件约 100 KB |
| `get_rows` | worktree、文件、侧（未暂存 / 已暂存）、视图（并排 / 统一）、`from`、`to` | 该区间显示行：行类型、旧/新行号、文本（并排行给左右两段）、所属 hunk | 500 行约 40–80 KB |
| `highlight_range` | worktree、文件、版本（HEAD / 暂存区 / 工作区）、行区间 | 逐行 token（颜色按调色板索引） | 400 行约 40–60 KB |
| `row_index_for_line` | 文件、视图、行号 | 行号在该视图里的显示行下标 | < 1 KB |
| `list_repos` / `add_repo` / `select_repo` | — | Revia 数据目录中的仓库列表与当前仓库 | < 2 KB |
| `check_environment` | — | git 是否可用、版本是否达标、环境解析是否回退 | < 2 KB |

约定：

- **不返回原始 patch**，前端拿不到也不需要 diff 文本；
- 每次返回都带 `fingerprint`（当前 worktree + 文件的 diff 指纹），为 M2 的写操作校验（ADR-0005）预留；
- **高亮只传可见行**，且只传“行 → token”，不传文件内容（M0 的 `get_file_versions` 因此删除，前端不再接触文件内容）；
- 编码先用 JSON。调色板索引可以把 token 载荷压掉约 40%（不再重复 7 字符的十六进制颜色），作为 M1 内的一个小优化；只有在实测超标时才动用 `tauri::ipc::Response`（二进制）或 `Channel`（流式）。

### 2.3 Rust 侧模型与缓存

新增 workspace 会话（每个 worktree 一个）：

```text
Workspace
├─ 环境（登录 shell 解析结果，M0 已验证）
├─ 状态快照：git status --porcelain=v2 -z 解析结果
└─ 文件模型缓存（按 文件 + 侧 键）
   ├─ 解析后的 hunk（来自 git diff，ADR-0004）
   ├─ 统一视图行索引 / 并排视图行索引（显示行 → 行号、hunk 归属）
   ├─ 行文本（按需切片）
   └─ 指纹
```

要点：

- **显示行索引放在 Rust 侧**。并排视图的“删除行与新增行配对”只是排版，不改变 hunk 划分；放在 Rust 侧后，`get_rows` 可以直接按显示行区间切片，前端无需先拿到整表再自己对齐。
- 索引是 `O(改动行数)` 的轻量结构（每行一个 kind + 两个行号），构建一次即可，成本与 M0 的解析阶段相同（实测整仓 diff 解析 12 ms）。
- 缓存按 **worktree + 指纹** 失效；M1 没有写操作，失效只发生在手动刷新、窗口重新获得焦点、切换仓库时。
- 路径处理沿用 M0 结论：所有返回路径的 Git 调用固定带 `-c core.quotePath=false`。

### 2.4 前端窗口化与预取

- 行高固定（等宽字体单行，不换行），因此窗口化只需要“区间 → 行下标”的算术。
- **分块大小 500 行**，前端维护“当前文件 + 视图”的块缓存（LRU，上限约 20 块 ≈ 10 000 行）。
- 取数策略：
  1. 可见区间（含 1 屏上下 overscan）所需的块必须齐备；
  2. 额外预取滚动方向上的下一块；
  3. 滚动位置一次变化超过 2 屏时判定为“大幅跳转”，取消在途请求并优先取目标块；
  4. 同一时刻最多 2 个在途请求，按块去重；切文件 / 切视图 / 切侧时递增代际，丢弃过期响应。
- 渲染：只渲染可见区间 + overscan 的行组件，行组件按（文件、视图、行下标）记忆化，滚动位置用单独的订阅源（`useSyncExternalStore`）驱动，避免整棵组件树重渲染。

### 2.5 消除空白的措施

M0 的空白来自“渲染跟不上滚动”，M1 会同时处理数据与渲染两侧：

| 措施 | 作用 |
| --- | --- |
| 数据分块缓存 + 1 块预取 | 快速滚动时目标行通常已在内存里 |
| overscan 从 24 行提高到 1 屏（约 47 行）× 上下两侧 | 合成期间即使落后一屏也不会露白 |
| 大幅跳转时“撤销在途 + 优先目标块” | 拖滚动条后内容尽快到位 |
| 行容器开启 `contain: strict`，行内容不触发重新布局 | 降低每帧的排版成本 |
| 数据未就绪时渲染**行号占位行**（已知行号来自已取到的相邻块边界与 `row_index_for_line`），而不是空白 | 即使数据迟到也不出现空白区 |

- 占位策略是保底手段：先做前四条，用验收测量（T2/T3）确认是否还需要占位；需要时按上面的方式补。

### 2.6 高亮通路

- 沿用 ADR-0006 与 M0 已验证的形态：syntect 在 Rust 侧、专用线程、**完整文件上下文**（旧、新两个版本各自完整解析）、解析状态按文件缓存、按行范围返回。
- 高亮不进首屏路径：文本先渲染，颜色到达后替换。
- 请求只针对**当前可见行范围**（400 行一块，可见区域优先，其余在后台补齐），并在滚动后按需补取；
- 主题暂定 `Solarized (light)`；亮/暗色跟随系统留到 M4（设置项属于 Q39 的后续范围）。

### 2.7 验收标准与测量方法

验收标准（技术方向）：同一组 M0 测试数据、release 构建、**在有图形界面的正常桌面会话中**：

| 编号 | 指标 | 目标 |
| --- | --- | --- |
| T1 | 选中文件（或恢复上次选中）到可见行文本提交到 DOM，不含高亮 | < 150 ms |
| T2 | 拖动滚动条大幅跳转后，目标窗口文本提交 | ≤ 1 帧（16.7 ms） |
| T3 | 触控板快速滑动期间，「可见行未取到数据」的帧数 | 0（并由人工确认无肉眼可见空白） |
| T4 | 滚动帧间隔 p95（有合成帧的会话） | ≤ 16.7 ms |

测量实现：

- 应用内测量面板（沿用 M0 思路）记录 `parseMs / ipcMs / renderMs / firstScreenMs`、每帧「未覆盖行数」、跳转耗时、帧间隔分布、窗口可见性与 rAF 次数；
- 结果写 JSON 到环境变量指定的路径，便于脚本比对；
- 脚本显式记录 `visibilityState` 与 rAF，**无合成的会话数据不当作验收结论**，只作为回归参考；
- 交付时由用户在正常桌面会话中运行一次并确认 T3 的肉眼结果（与 M0 相同的做法）。

### 3.3 shadcn/ui 组件基座：Base UI

选 **Base UI**（`shadcn init -b base`）。依据：

- shadcn/ui 官方在 2026 年 7 月把 **Base UI 设为新项目默认基座**（Radix 仍然完整支持、未弃用），文档与组件页也默认展示 Base UI 标签页。来源：[Base UI as the Default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)。
- 基座只影响底层无样式组件（Tooltip、Popover、Switch 等），源码生成后由项目维护；Radix 与 Base UI 的差异不影响 Revia 的界面方向。
- 现在选 Base UI，等同于跟官方默认路径一致，避免后续在两种基座之间迁移。

M1 用到的组件（按官方目录）：Button、Input、Separator、Tooltip、Toggle Group（并排 / 统一切换）、Badge（计数）、Empty（首次打开）、Scroll Area（备选）、Resizable（面板宽度，可选）。

### 3.4 类型同步

- 用 `ts-rs` 从 Rust 结构体生成 TS 类型，生成物提交进仓库（`src/types/bindings/`），前端 `lib/ipc/` 只写固定命令的薄封装；
- 不引入 `tauri-specta`：v2 目前仍是候选版（`2.0.0-rc.25`），作为基础依赖风险偏高；等它稳定后可再切换（切换只影响封装层）；
- 每次改动 Rust 侧数据结构后跑一次生成脚本，并在 CI 之外用 `pnpm typecheck` 兜底。

## 六、风险与备选

| 风险 | 说明 | 备选 |
| --- | --- | --- |
| 自绘窗口化 + 预取的复杂度 | 需要自己处理代际取消、预取、占位 | 改用 `@tanstack/react-virtual`（3.x）做区间计算，但数据预取仍是自研 |
| 大仓库首次列表 | 首次 `list_changes` 需要完整解析 diff；M0 在 1.15 MB 上 12 ms，更大的仓库可能到几百毫秒 | 按文件分批解析并先返回文件列表，diff 解析放到后台任务；必要时加进度 |
| 高亮跟不上快速滚动 | 颜色会滞后；不可接受的只是空白 | 高亮块大小按实测调整；最后手段是把高亮限制在停稳后 100 ms |
| 首次实测环境无合成 | 实现方会话没有图形合成，无法直接得出验收数字 | 交付一键测量脚本 + 用户在正常会话中确认（M0 的做法） |
| Base UI 生态较新 | 个别组件的 API 与 Radix 略有差异 | 组件源码在本仓库，可替换单个组件；基座不混用 |
